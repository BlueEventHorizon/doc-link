# 検索の担当分割・1 件ずつの回答・3 値の関連の強弱に関する、未確認事項と懸念

検索（`query-docs`）を、文書を担当に分けて並列に読み、1 件ずつ答え、関連の強弱を `yes`・`maybe`・`no` の 3 値にする方式へ改めた変更（Issue #19・#21、commit `969962a`）について、実装・検証の時点で気づいた違和感と問題の可能性を残す。仕様ではない。仕様は DES-006 §2・DES-010 §4 にある。

各項目に、確認の状態を付ける。「確認済み」は、コードや実行結果で見たもの。「未確認」は、記憶・推測・報告によるもので、確かめていない。

## 1. 連携先・要件との境界

- **結果の形が利用者に見えるものへ変わった（要件との境界）** — 確認済み（変更の事実）／未判断（扱い）
  - `relevance` が付き、並びが関連度順でなくなり、`rejected` が無くなった。
  - 設計の変更として扱ったが、判定の基準は「ユーザーマニュアルに書く内容か」である。利用者に見える結果の形なので、要件（REQ-004）に書くべきではないかを、再確認する必要がある。
- **forge 経由で、`maybe` と `yes` の区別が消える可能性** — 手順の記述を読んで確認／実動作は未確認
  - `forge:query-db-*` の手順は、結果のパスを「返された順のまま」渡して `Required documents:` に整える。`relevance` は渡らないはずである。
  - forge 経由では `maybe` も `yes` と同列に見え、並びを関連度順と誤読されやすい。
- **破壊的変更の影響範囲** — 未確認
  - `query_docs.py` のサブコマンド（`request-path`・`submit-item`・`submit-end`）の廃止と、結果の項目の変更（`rejected` の廃止、`relevance`・`order_notice` の追加）が、forge など外部から使われていないかを、探していない。

## 2. 設計上の懸念

- **答えの位置ずれ（無言の取り違え）の対策が無い** — 確認済み（仕組み）／検証では 0 件
  - `answer` が実行されたのに、worker が結果を受け取れず再送すると、前の答えが次の文書に付く。検出する仕組みが無い。
- **前方一致の誤選択の可能性** — 確認済み（仕組み）／検証では起きていない
  - 短い断片（例: `2`）が 1 つの見出しにだけ一致すると、意図と違うセクションでも拒否されずに確定する。
- **担当の割り当てがパスの昇順** — 確認済み
  - 同じディレクトリの文書が 1 本に固まり、担当ごとの判断が偏りやすい。検証でも、担当 2 だけ `yes` が 0 件だった（consult の文書が集まったため）。交互の割り当てなら偏りは減るはずだが、検証していない。
- **1 本あたりの件数に上限が無い（設計でも TBD）** — 確認済み
  - 400 件は 1 本 40 件で収まる見込みだが、4,000 件なら 1 本 400 件になり、元の問題（1 本の context に収まらない）に戻る。最小件数（10）も暫定値である。
- **1 件あたり 2 往復（Bash と Read）** — 確認済み
  - 受け渡し規約が、stdout に JSON 本文を載せないと定めているため。規約を変えれば 1 往復にできる。1 件あたり約 5〜6 秒を測った。

## 3. 検証の不足

- 検証は、1 つのタスク、44 文書、2 回（2 値と 3 値）である。全 ToC を読む旧方式との精度比較は、していない。
- `yes` と `maybe` の分かれ方が、担当間で揃うかは、1 回の結果では判断できない。
- 400 件規模の実走は、していない（見込みは 1 本 40 件で約 4 分）。
- 担当 1 の worker が、指示にない `ls`（作業ディレクトリの確認）を 1 回実行した。読み取りのみで、結果に影響はない。Bash の中身は、agent 定義では制限できない。
- サブエージェントの作業ディレクトリは、親の `cd` に追随しない。そのため、検証用の使い捨てプロジェクトを、このリポジトリの中に置く必要があった。通常の利用では問題になりにくい。cwd がプロジェクトの外にあると、検索は失敗として返る（安全側）。
