# DES-002 実行主体と処理責務

**状態**: 承認済み\
**更新日**: 2026-10-31\
**根拠**: [要件の責務境界][req-001-sec-5-3]、[設計書の構成][readme]

<a id="sec-1"></a>

## 1. 責務と権限

| 主体                            | 担うこと                                                                                          | 書き込み権限と禁止事項                                                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 呼び出し元・プロジェクト管理 AI | 管理キーと完全な対象指定を渡す。通知をプロジェクト文脈で判断し、本文・リンクを修正する            | 文書 ID の採番、ToC の直接編集をしない                                                                                                                                  |
| doc-link Skill                  | 操作を選択し、script と内部 AI を順序付ける。検索時に必要な利用者確認を取り、結果を返す           | 検査結果や ToC を自由記述で上書きしない。script のガードを迂回しない                                                                                                    |
| 決定論的な script 群            | 走査、解析、ID 管理、差分、ハッシュ、参照検査、生成結果検証、ToC 候補検査・確定、状態遷移のガード | DLID の書き込み（frontmatter・アンカー行・リンクの title）と doc-link 管理状態の更新だけを行う。DLID の書き込みは ID 付与操作に限る。それ以外の本文・リンクは修正しない |
| 情報生成 AI                     | 対象文書から目的・概要・適用作業・キーワードなどを生成する                                        | ID、ハッシュ、参照検査状態、ToC を直接変更しない                                                                                                                        |
| 検索 AI                         | 確定版の ToC 全体を読み、タスクに関連する文書と関連理由を返す                                     | 存在しない ID を補わない。索引の版・パスを訂正しない。ToC と管理状態を変更しない                                                                                        |
| ユーザー                        | ToC が古い場合、更新後に検索するか、古い版で検索するかを選ぶ。ID 重複の原本を確定する             | 選択なしに古い版を現在状態として扱わせない                                                                                                                              |

ここでの「script 群」は検証可能な決定論的処理の論理的な担当を表す。実際のスクリプトの本数、ファイル名、実装言語は後続設計で決める。要約などの AI 生成結果は script の入力となり、script が型・長さなどを検査する。変更影響候補の列挙に AI の判断結果を入力しない。

<a id="sec-2"></a>

## 2. script が提供する論理的な操作

| 操作                 | 入力                                     | 成功結果                                               | 副作用・失敗時の約束                                                                                                              |
| -------------------- | ---------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 対象指定の展開       | キー、完全な指定                         | 正規化した指定と具体的な Markdown 一覧                 | 対象外の探索を行わない。不正指定なら後続へ進めない                                                                                |
| ID の確認            | 対象一覧                                 | 認識可能で重複のない ID と現在パスの一覧、除外した文書 | 書き込まない。ID 未付与・重複の文書を除外して報告する（要件 D-036）                                                               |
| ID 付与              | 対象の指定                               | 発行・書き込みした DLID、重複の原本候補                | DLID だけを書き、書き込み後に差分を検証する。重複は利用者が原本を確定してから、複製側に新しい ID を発行する（要件 D-029、D-031）  |
| 比較値の取得         | ID 確定済み一覧                          | 内容・参照・パスの比較値                               | 読取不能を変更なしと扱わない                                                                                                      |
| 差分判定             | 比較値、確定済み ToC、処理済み基準       | 併存可能な変更種別と更新計画                           | 要約生成や ToC 確定を行わない                                                                                                     |
| 参照の抽出・検査     | 参照元、記載パス、参照先 ID              | 参照記述と、ディレクトリ実走査による検査結果           | 指定ディレクトリ内不在とパス不一致を区別する                                                                                      |
| AI 出力の検証        | 生成結果、公開する記述上限、内部検証基準 | 受理した文書情報または拒否理由                         | 生成担当 AI に内部許容上限を開示しない                                                                                            |
| 候補の検査・確定     | 対象集合、比較値、文書情報、参照検査結果 | 検査済みの新しい ToC 版                                | 途中状態を公開せず、失敗時は最後の確定版を維持する                                                                                |
| 検索・逆引きの読取り | キー、確定版、検索条件                   | 文書・参照元の候補と使用版                             | 現物を見ずに現在の参照の正しさを断定しない                                                                                        |
| DLID の解決          | DLID の並び、管理状態                    | DLID ごとの現在パス、または記録されたパスに無いこと    | 書き込まない。記録されたパスの文書がその DLID を持つことを確かめてから返し、ほかの場所を探索しない（[DES-006 §3][des-006-sec-3]） |
| 処理済み基準の更新   | 報告する変更、現在比較値、旧基準         | 報告する対象の比較基準                                 | ToC 確定だけでは更新しない。更新できなかった場合は報告せず、旧基準を維持する                                                      |
| 不整合検査           | 対象指定、現物、確定版                   | 問題の一覧                                             | 書き込まない。ID の付与・修復は ID 付与操作が行う（要件 D-035）                                                                   |

検索の意味的な関連度は、読み取り専用の検索 AI（カスタム Agent）が ToC を読んで判定する（[DES-006 §2][des-006-sec-2]）。script は使用版・キー・文書 ID・パスを確定したデータから渡し、検索 AI は索引の状態を変更しない。

<a id="sec-3"></a>

## 3. Skill と script の接続規則

doc-link の各 Skill は、呼び出し元（プロジェクト管理 AI）のコンテキストでそのまま実行する継承型とする。SKILL とカスタム Agent の構成は [DES-010][des-010] に定める。Skill の実行と、通知を受けた本文・リンクの修正は同じ AI が行う。script は DLID の書き込みと管理状態の更新だけを担い、要約生成 AI だけを別のコンテキストに分ける（2 番目の規則）。

1. Skill は要件で定めた順序で操作を起動するが、「前段成功」という自己申告だけで次段に進めない。script は入力に含まれる版と状態を検査し、許可されない遷移を拒否する。
2. 要約生成 AI の入力コンテキストは生成対象の文書内容と記述上限 `L` に必要な情報だけで構成する。内部許容上限 `H`、係数、余白の存在は、プロンプト、再試行メッセージ、生成 AI が参照するルールへ渡さない。`H` を含む設計・検証情報を既に読んだ同一コンテキストを、そのまま生成担当として使用しない。検証器の情報境界は script が担う。
3. 変更影響候補の通知では、script が変更文書と把握済み参照元を機械的に列挙し、Skill が依頼元へ返す。doc-link 内で修正要否の判断、理由の生成、修正案の作成を行わない。
4. プロジェクト管理 AI が修正した後の再検査は新しい操作として起動する。doc-link が管理対象 Markdown の本文・参照リンクを直接修正する経路を設けない。
5. 検査・検索・DLID の解決・構築・変更影響候補の通知は異なる script 操作とする。SKILL への割り当ては DES-010 に従う。検査の SKILL は管理状態を書き換えない。ただし `check-impact` は、報告を返すときに処理済み比較基準を進める（要件 D-038、[DES-007 §3][des-007-sec-3]）。「不整合を報告する検査」と「ID を付与する操作」を同じ SKILL にしない。

<a id="sec-4"></a>

## 4. 保留と後続設計

ID 付与操作が ID を一部の文書へ保存した後に失敗した場合、既発行 ID は不変として再実行時に再利用する必要がある。書き込み済みの DLID は正しい値なのでロールバックせず、発行済みとして報告し、再実行で残りを処理する（要件 NFR-003、NFR-006）。script の分割、CLI の引数形式は後続設計で扱う。Python の script は `uv run` で実行し、Python 本体と外部依存（PyYAML、markdown-it-py）は uv が用意する。利用者の環境の前提は uv だけとする。

doc-link が作るファイルは、すべてプロジェクトの中に置き、プロジェクトの外（OS の一時ディレクトリなど）には作らない。一時ファイル（書き込み用の一時ファイル、カスタム Agent との受け渡しファイル、検索に渡す ToC の写し）は、[実装ガイドライン][implementation-guidelines] に従い `.temp/doc-link/<skill>/` に置く。

doc-link の管理状態は、プロジェクトルート直下の `.doc-link/` に JSON ファイルとして保存し、git で追跡する（決定: 要件 U-010、U-011）。並行するブランチで更新しても衝突が差分として読めるよう、次の 3 種類のファイルに分ける。

- 文書情報：文書 ID ごとに 1 ファイルとする。二つのブランチで衝突するのは、両方で同じ文書を変えた場合に限られる。
- キー別の索引状態（ToC の確定版）：管理キーごとに 1 ファイルとする。
- 処理済み比較基準：全体で 1 ファイルとする。`check-impact` は報告する組の比較基準をまとめて進めるため（[DES-007 §3][des-007-sec-3]）、1 回の書き込みで全組を更新する。

script は同じ内容から常に同じバイト列を出力する（UTF-8、オブジェクトのキーの並べ替え、インデントの固定）。内容が変わらないファイルは書き換えない。文書情報とキー別の索引状態のファイルが衝突した場合は、どちらかの内容を採って構築を再実行すれば、内容ハッシュが変わった文書だけの AI 生成で収束する。書き込みの単位は [DES-005 §5][des-005-sec-5] に定める。
