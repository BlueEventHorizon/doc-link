# DES-006 文書検索設計 DLID-wwna81gbj3jz

<a id="sec-1"></a>

## 1. 検索前の判定 DLID-ksmh21dbz9zv

検索要求はキー（省略時は予約キー `all`）とタスク・検索条件を持つ。指定キーの[確定 ToC]がなければ、検索せず初回構築が必要と返す。[確定 ToC]があれば、その版に保存した再解釈可能な対象指定で現在の一覧を走査し、ID、パス、比較値を版と照合する。新しい完全な対象指定が同時に与えられた場合はそれを優先する。その指定が版に保存した指定と違うときは、文書に差が無くても、再構築が必要と判定する（要件 [D-053][req-003-sec-7-5]）。対象指定の展開・現物の読取りが失敗した場合は「更新不要」と判定しない。

検索前検査の結果は「再構築不要」「再構築必要」「判定不能」を区別する。この区別は[検索基盤]によらない。再構築が必要なときの扱いは、[検索基盤]で異なる。[検索基盤]が[doc-db]のときは、二択を示さず、自動で更新してから検索する（[DES-011 §7.1][des-011-sec-7-1]）。[検索基盤]が[ToC]のときの扱いを、以下に示す。

比較で再構築不要なら[確定 ToC]を検索する。再構築が必要なら Skill がユーザーへ「再構築後に検索」「既存版のまま検索」の二択を確認する。確認時には script が照合結果から数えた再構築の規模（新規・離脱・パス変更・内容変更・ID 未付与・ID 重複の件数と、同じ[内容ハッシュ]の[文書情報]がなく AI 生成が必要な件数）を示す（要件 [D-027][req-004-fr-006]）。標準出力に返すのは件数までで、変更のある文書・セクションごとの明細は、`.temp/doc-link/query-docs/` の明細ファイルへ書いて、その絶対パスを返す（要件 [D-061][req-005-fr-016]）。あわせて、検査に使った[ToC 識別キー]と[Index 対象指定]を、`.temp/doc-link/query-docs/target-<符号化した[ToC 識別キー]>.json` の対象指定ファイルへ書いて、その絶対パスを返す。再構築（`index-docs`）と、再構築の後にやり直す検索前検査は、このファイルを `--target-file` で受け取る。AI は対象指定を引数へ書き写さず、返されたパスだけを運ぶ。再構築が別の対象で行われたときは、やり直した検索前検査が、このファイルの指定と[確定 ToC]の指定の違いを再構築必要として検出し、検索を停止する。対象指定ファイルは、同じ[ToC 識別キー]の次の確認で置き換える（要件 [D-063][req-004-fr-006]）。参照先の走査結果と生成にかかる時間はこの時点では分からないため示さない。前者は[DES-005][des-005]が正常確定した場合だけ新版を検索し、失敗時に旧版で黙って検索しない。後者は[ToC]に書き込まず、結果に古い版であることを明示する。古い版から使うのは所属であり、[文書情報]は最新のものを表示する（要件 [D-024][req-003-fr-004]）。検索は確定済みのファイルを読む。

対象指定の展開または現物の読取りに失敗した「判定不能」は、再構築不要・再構築必要のどちらにも読み替えない。判定不能は障害として扱い、検索を停止して、判定できなかった対象と原因を返す。旧版での検索を利用者に提示しない（要件 [D-026][req-004-fr-006]）。frontmatter の解析不能（ID 欠落扱い）や対象ディレクトリの消失（対象離脱）は判定不能ではない。前者は ID 未付与として件数を示し（要件 [D-036][req-002-sec-9-1]）、後者は再構築必要に分類する。

## 2. 検索結果の契約 DLID-p07g3hc4e4xd

各候補は[文書 ID]、[確定 ToC]に記録されたパス、関連の強弱、関連理由、必要ならセクション、使用した[ToC 識別キー]・[ToC]版・鮮度判定を持つ。以下は[検索基盤]が[ToC]のときの検索である。[検索基盤]が[doc-db]のときは、同じ項目を[DES-011 §7.4][des-011-sec-7-4]のとおり満たす（関連の強弱は `maybe` の固定、上位の結果に限られる）。「既存版のまま」を選んだ場合は、その版が現在の[Index 対象リスト]を反映していない可能性を結果全体にも付ける。文書が現物で移動・削除されていても、古い索引のパスを現在の実体パスとして断定しない。

script は[確定 ToC]と入力キーに基づき、検索に使う[ToC]と版・鮮度を固定する。自然言語タスクとの意味的な関連度は、読み取り専用の[検索 AI]（カスタム Agent）が、文書を 1 件ずつ読んで判定する。固定した[ToC]のすべての文書が、いずれかの[検索 AI]に読まれる。[ToC]を語句の一致で絞り込んで済ませない。選ぶときは、取りこぼしを出さないことを優先する。タスクに関連するか迷う文書は選び、明らかに無関係な文書だけを選ばない（要件 [D-056][req-004-fr-006]）。選んだ文書を、関連の強弱と関連理由とともに返す。関連の強弱は、`yes`（関連する）、`maybe`（判断がつかないが、関連するかもしれない。取りこぼさないために結果に含める）の 2 つである。明らかに無関係な文書は `no` として結果に含めない。点数や順位は付けない。

script は、固定した[ToC]の文書を、[検索 AI]の担当に分ける。1 回の検索で起動する[検索 AI]の数は、script が決める。同時に起動する数の上限（`index-docs` の生成と同じ 10 本）を超えず、文書の数をその数で割った件数ずつを、担当ごとに割り当てる。文書が少ないときは、1 本あたりの件数が小さくなりすぎないよう、起動する数を減らす（1 本あたりの最小件数は TBD。script の定数とし、実測で決める）。担当と割り当ては script が決めて、固定した状態に持つ。AI は、文書の件数も担当の数も数えない。1 本が受け持つ件数は、文書が増えると増える。担当の件数に上限を設けるかは、この設計では定めない（TBD）。

script が[検索 AI]に見せる内容（以下、見せる内容）は、script が検索に使う版の[確定 ToC]の所属と、所属する文書の[文書情報]から組み立てる（[DES-003 §2][des-003-sec-2]）。見せる内容は次のとおり。

- 文書ごとに、[文書情報]のタイトル・目的・内容概要・適用作業・キーワードを入れる。[文書 ID]は入れない
- セクションごとに、見出しを入れる。[セクション ID]は入れない
- 見出しは、[検索 AI]がセクションを答えるときの名前になる。同じ見出しが 1 つの文書に複数あるときは、script が `（同名 k/n）` を足して、名前を一意にする。一意かどうかは、全角半角と空白を正規化して比べる。名前と[セクション ID]の対応は、script が固定した状態に持つ。タイトルは読むための情報であり、答えには使わない
- パスは入れない。[文書 ID]・[セクション ID]とパスは script が付ける
- [内容ハッシュ]、参照関係、検査結果は入れない。意味的な関連の判断に使わないためである

[検索 AI]は、script から文書を 1 件ずつ受け取り、その文書に答える。どの文書への答えかは、script が持つ位置で決まる。[検索 AI]は、文書を指す名前も、[文書 ID]・[セクション ID]・番号も、見ず、書かない。[文書 ID]・[セクション ID]はランダムな文字列で、書き写しの誤りが起き、番号は、覚えて書く点が同じである。文書の名前を書き写させる方式は、文書が増えると書き写す量が増え、誤りが増える。答えは JSON で、関連の強弱（`yes`・`maybe`・`no` の 3 つの語のどれかだけ。数や真偽値ではない）を持つ。`yes` と `maybe` は、関連理由と、必要ならセクションの見出しを持つ。`no` は、関連の強弱だけを持つ。強弱を数字ではなく、閉じた少数の語にするのは、点数は[検索 AI]ごとの基準がずれやすく、結果の検査と比較ができないためである。要件は変わらない。呼び出し元へ返す結果は、これまでどおり[文書 ID]を持つ。

worker は存在しない見出しを作らず、索引の版・パスを訂正せず、[ToC]と管理状態を変更しない。

script は、答えを受け取った時点で検査する。形式（JSON として読めること、キーと型）が合わないとき、または答えの見出しが、その文書のセクションの見出しに引き当てられないときは、何も保存せず、直すべき箇所を返す。見出しは、その文書のセクションの中だけから、正規化（全角半角・空白）した完全一致、または、その文書の中で一意に決まる前方一致で引く。引き当てられないときは、その文書の見出しの候補（写しにある正しい文字列）を添えて返す。[検索 AI]は、同じ文書に答え直せる。script は、近い見出しで読み替えて補わない。引き当てられない答えは、保存されず、黙って捨てられることもない。保存した答えは、上書きしない。

検索の終了は、担当のすべての文書に答えが保存されたことで決まる。いずれかの担当で、答えの保存されていない文書が残っているとき（[検索 AI]が途中で終えた）は、関連する文書が無い正常な 0 件と見分けられないので、検索を失敗とする。すべての文書に答えがあり、関連する文書が 0 件のときは、正常な 0 件である。

結果の文書の並びは、script が決めた担当の順と、担当の中の順であり、関連度の順ではない。[検索 AI]は順位を付けない。関連の強弱は、並びではなく、各文書の `relevance`（`yes`・`maybe`）が持つ。呼び出し元は、これで読む優先度を決める。`maybe` を `yes` に読み替えない。

## 3. [DLID]の解決 DLID-m0xegzfyhc3k

`resolve-dlid` は[DLID]の並びを受け取り、[DLID]ごとに解決結果を返す（要件 [FR-018][req-002-fr-018]）。[ToC 識別キー]は受け取らない。解決は確定済みの管理状態の記録と、記録されたパスの現物だけで行う。

1. 文書の[DLID]は、その[文書情報]に記録された現在パスを引く（[DES-003 §2][des-003-sec-2]）。[セクション ID]は、全キーの[確定 ToC]のセクションエントリから所属する[文書 ID]を引き、その[文書情報]の現在パスを使う。セクションを別の文書へ移した後、移動元の文書を含むキーを再構築していないと、移動元と移動先の両方の文書に同じ[セクション ID]が記録されている。この場合は記録された所属文書をすべて候補にする。
2. 記録されたパスのファイルを読み、文書の[DLID]は frontmatter の `doc_link_id` と、[セクション ID]は見出しの行の末尾の[DLID]と照合する（[DES-008 §1][des-008-sec-1]）。一致すれば「解決済み」としてパスを返す。セクションには見出しの文字列と、見出しから生成されるアンカー（要件 [D-048][req-005-fr-009]）を添える。
   - あわせて[内容ハッシュ]を添える。文書は[文書情報]の[内容ハッシュ]、セクションは所属文書の[文書情報]のセクションエントリのセクション単位のハッシュである。
   - 現物からは計算しない。
   - ハッシュを得られないときは、[内容ハッシュ]を添えず、その旨を返す。ひとつ前の保存形式の[確定 ToC]が残っていて、セクションのハッシュが記録によって異なるときも、同じである。
3. ファイルが無い場合と[DLID]が一致しない場合は、記録されたパスを添えて「記録されたパスに無い」と返す。候補が複数あるときは、一致した候補だけを解決済みとし、どれも一致しなければ記録されたパスをすべて添える。ほかの場所を探索しない。§2 と同じく、記録されたパスを現在の実体パスとして断定しない。ファイルを読めない場合も、確かめられないので「記録されたパスに無い」と返す（要件 [FR-018][req-002-fr-018]）。記録されたパスがシンボリックリンクで、実体がプロジェクトの外にあるときは、実体を読んで照合する。構築が同じ実体を読んで記録しているためである（要件 [D-049][req-002-sec-6-1-4]）。記録されたパスそのものが、字面でプロジェクトの外へ出る（絶対パスや `..` で始まる）ときは、不正な記録として読まず、「記録されたパスに無い」と返す。記録はその文書を含む[ToC]を再構築すると更新される。
4. どの記録にも無い[DLID]は「記録が無い」と返す。管理状態を読み取れない場合は全体を失敗とし、原因を返す。

[ToC]、管理状態、[Index 対象文書]には書き込まない。
