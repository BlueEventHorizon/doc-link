# doc-link 実装戦略

## 前提の確認

- 型の判定: `feature_marker.py` の結果は、要件定義書 5 件・設計書 10 件のすべてでマーカー無し。既存の要件定義書・設計書は doc-link のものだけで、旧仕様は無い。差分開発型ではなく、完全新規として扱う。このため「既存実装との不一致」の節は置かない。
- 既存コードの調査（該当なし）: `plugins/doc-link/` にあるのは `.claude-plugin/plugin.json` だけで、script・SKILL・Agent は無い。`tests/doc-link/` は空。再利用できる既存資産・兄弟機能は無い。`plugin.json` の version は編集しない。
- 既存の仕様書の調査: backend の索引検索は実行せず、`.doc_structure.yaml` が指す `docs/specs/**` の配下を列挙して確認した。`requirement/`・`design/` は doc-link の文書だけで、`adr/` は空。他の仕様に依存・接続する記述は設計書に無い。索引検索を経ていないので、未索引の仕様が別の場所にある可能性は検証していない。
- 要件と設計の食い違い: 読んだ範囲で、依って立つ文書どうしの矛盾は見つからなかった。設計書 README の「確定を妨げる判断待ち」も無い。

## アプローチ

**選択**: リスク駆動を軸に、ボトムアップで積み上げる。最後にスケルトン先行ではなく横断シナリオで結合を検証する。

**根拠**:

- 最も危険なのは、利用者の文書へ書き込む `embed-dlid` と、その土台の Markdown 解析・ハッシュ規則である（NFR-004、DES-008）。ここを誤ると、利用者の文書を壊し、以降のすべてのハッシュと参照が連鎖して狂う。最初のフェーズに置く。
- 依存は一方向に深い。解析・ID・対象展開・管理状態の保存が、構築（`index-docs`）の土台になる。構築の確定結果を、検索・解決・各検査が読む（DES-001 §2）。そのため土台から積むボトムアップが自然である。
- AI が介在するのは `toc-updater` と `query-worker` だけで、受け渡しは識別値と終了の値という定型で閉じる（DES-010 §4）。AI なしで決定論的に検証できる部分を先に固め、AI の接続は後のフェーズで差し込む。
- 設計が script を決定論的な操作の集合として分けており（DES-002 §2）、各操作を単体で検証できる。

## フェーズ

### フェーズ 1: 土台と DLID 付与（`embed-dlid`）

- **目標**: Markdown 解析、DLID、ハッシュ、対象指定の展開、管理状態の保存が決定論的に動く。`embed-dlid` が、指定した文書の `doc_link_id` と全見出しの末尾へ DLID だけを書き込み、書き込み後の再解析で差分が DLID だけであることを検証できる。
- **スコープ**:
  - Markdown の読取り規則: frontmatter の判定、`doc_link_id` の認識、見出しとセクションの範囲、リファレンスリンクの定義の抽出、アンカー生成（DES-008 §1・§2）
  - DLID の発行・認識と、[内容ハッシュ]の算出（title の記録語を除く規則を含む）（DES-008 §1・§3、要件 D-028・D-039）
  - 対象指定の検証・展開、固定の除外、パスの正規化（DES-005 §2 の 1・2）
  - 管理状態の保存層: `.doc-link/` の決定論的な JSON 出力、一時ファイルと `os.replace` による置き換え（DES-002 §4、DES-005 §5）
  - `embed-dlid` の script と SKILL: 重複の照合、原本候補の提示、書き込み・差分検証・取消し（DES-004 §5、DES-005 §2.1、DES-010 §3.1）
  - プラグイン共通のスクリプトは `plugins/doc-link/scripts/` に置く。複数の SKILL が使うため。他の SKILL の `skills/{skill}/` 配下は参照しない（実装ガイドライン）。
- **検証ポイント**:
  - 最初の動作確認の時点を、解析規則とハッシュのテストベクトルが通った時点に置く。これは `embed-dlid` の実装より前に行う。DES-008 §3 のテストベクトル（本文・見出し・リンクの変更でハッシュが変わる、title の記録語の書き換えでは変わらない、相互参照の文書で連鎖しない、セクション範囲外の変更で変わらない）、CommonMark 規則 1〜10 が markdown-it-py で期待どおりになること、アンカー生成が github-slugger と一致することを確認する。
  - `embed-dlid` については、固定の入力文書（ATX・setext・閉じの `#`・コードブロック内の見出し・frontmatter なし・閉じる行なし）で、書き込み後の差分が DLID だけになること、閉じる行のない文書には書かないこと、差分が DLID 以外にあれば取り消すこと、再実行で差分が出ないこと（冪等）を確認する。
  - E-01〜E-07 の全遷移と、ガード不成立・表にない遷移の拒否をテストする（DES-009 §1）。
  - 全 script が `uv run` で動き、PEP 723 の宣言とロックを持つ。テストは `tests/doc-link/` に置く。`dprint check` が通る。

### フェーズ 2: 参照検査と `index-docs`（`toc-updater`）

- **目標**: `index-docs` が、対象確定から [確定 ToC] の一括公開までを段階どおりに進め、旧 [確定 ToC] を保ったまま失敗を扱える。2 回目以降は変更のない文書で AI を呼ばない。ID 未付与・重複の文書は [ToC] に入れず報告し、構築は続ける。参照の実走査の結果（一致・パス不一致・不在・フラグメント不一致）が [ToC] に記録される。
- **スコープ**:
  - ID 確認と除外の報告（DES-005 §2 の 3、要件 D-036）
  - 変更集合の確定: 新規・本文変更・参照変更・移動・離脱・変更なしを併存可能に保持（DES-005 §3、DES-004 B-03）
  - 参照の抽出と、指定ディレクトリの実走査による検査（DES-007 §1、DES-008 §2 の規則 1〜10）
  - 更新計画、[文書情報]の文書単位の保存、[ToC 候補]の検査と一括公開（DES-005 §4・§5、DES-004 P-01〜P-03・B-01〜B-09）
  - AI 出力の検証器（`H = floor(L × 1.3)` と要素数の下限）、`toc-updater` の定義と依頼・結果の受け渡し script（DES-008 §4、DES-010 §4、`agent_data_exchange_rules.md`）
  - `index-docs` の入口 script（段階を進め、次に SKILL が行うことを返す）と SKILL（DES-010 §3.2）
- **検証ポイント**:
  - 最初の動作確認の時点は、AI を介さず、生成結果を固定値で差し込んだ構築が通った時点とする。この時点で、初回確定、再実行の冪等、旧版の保持、複数キーの隔離を確認する。その後に `toc-updater` を接続する。
  - P-01〜P-03、B-01〜B-09 の全遷移と拒否の確認。各段階の失敗位置で、旧 [確定 ToC] の扱いと、確定済みの[文書情報]が戻らないことを区別して確認する。
  - 検証器の境界テスト（`L`、`L + 1`、`H`、`H + 1`）。`toc-updater` に渡る依頼・プロンプト・再試行メッセージに `H`・係数 `1.3`・余白が含まれないことの検査（AC-010・AC-011）。
  - 受け渡しの確認: 識別値だけが運ばれ、script が書き、書き終えてから公開され、終了の値が `"0"` 以外または無いときは失敗として扱われ、処理後に削除される。
  - 参照検査: 一致・パス不一致・不在・ディレクトリを読めない・ディレクトリ自体が無いの各場合に、確定が止まらないこと（AC-028）。
  - 実際の `toc-updater` の生成品質は AI の判断なので、自動テストに入れず手動の確認として分けて残す（実装ガイドライン「テスト」）。

### フェーズ 3: 読み取り専用の SKILL（検査・解決・検索）

- **目標**: `check-dlid`・`check-links`・`check-toc`・`check-impact`・`resolve-dlid`・`query-docs`（と `query-worker`）が、管理状態と [Index 対象文書] を一切書き換えずに動く。
- **スコープ**:
  - `check-toc` と、`query-docs` の検索前検査が使う共通の照合 script（再構築不要・必要・判定不能・未構築の区別と、規模の件数）（DES-006 §1、DES-010 §1.2）
  - `check-dlid`（DES-005 §2、DES-010 §3.4）
  - `check-links`: 壊れた参照、title に DLID の無いリンク、インラインリンク、フラグメント不一致と現在のアンカー（DES-007 §1・§4、DES-010 §3.5）
  - `check-impact`: 記録と [現在ハッシュ] の比較、直接の参照元だけの列挙、[ToC] が古いときは候補を返さず `check-toc` の結果を返す（DES-007 §2・§3、DES-010 §3.7）
  - `resolve-dlid`（DES-006 §3、DES-010 §3.8）
  - `query-docs` と `query-worker`: 検索に渡す [ToC] の写しの組み立て、利用者への二択の確認、返った ID の検査（DES-006 §1・§2、DES-010 §3.3・§4）
- **検証ポイント**:
  - 最初の動作確認の時点は、フェーズ 2 の構築結果を入力にした `check-toc` と `resolve-dlid` が通った時点とする。この 2 つは、ほかの SKILL が使う照合と記録の読取りを含む。
  - 全 SKILL で、実行の前後に管理状態と [Index 対象文書] がバイト単位で変わらないこと。
  - `check-impact`: DES-009 §1 に列挙された全項目。記録の書き換えで通知が連鎖しないこと、相互参照の文書で通知が終わらなくならないこと、記録だけの書き換えで `check-toc` が [ToC] を古いと判定しないこと、失敗時にエラーの JSON を返し通知しないことを含む。
  - `resolve-dlid`: 移動後の再構築の前後（AC-031）、記録の無い DLID、管理状態を読めないときの失敗、セクションの内容ハッシュが記録によって異なるとき。
  - `query-docs`: 未構築、判定不能で停止して旧版の選択肢を出さないこと、二択、旧版で検索したときの鮮度の明示、[ToC] を更新しないこと（AC-019）。`query-worker` の判断品質は手動の確認とする。

### フェーズ 4: 横断シナリオと配布物の適合

- **目標**: 設計書の横断シナリオが、実際のプラグインの構成で通る。配布物がプロジェクトのルールに適合する。
- **スコープ**:
  - DES-009 §3 の横断シナリオ 1〜7（初回、移動、内容変更、失敗、複数キー、範囲外参照、後からの参照）
  - 要件の受け入れ条件と検証観点の対応（DES-009 §2）の抜けの確認
  - 配布物の適合: SKILL.md にロジックを書かない、継承型 SKILL と `context: fork` の不使用、カスタム Agent の Role 制約・禁止事項・allowlist、配布物から開発用の `docs/specs/`・`docs/rules/` を参照しない、script の終了コードの宣言（`script_error_output_rules.md`）、Node.js 不使用、一時ファイルの置き場
- **検証ポイント**:
  - 7 つの横断シナリオが、固定の入力から再現できること。
  - 全 `.py` にテストがあり、`unittest discover` が通る。`dprint check` が通る。
  - 配布物に開発文書へのパス・仕様 ID の参照が無いことの機械的な検索（検索語と範囲を残す）。
  - `plugin.json` の version と CHANGELOG を編集していないこと。

## リスクと対策

| リスク                                                                                                                                            | 影響度 | 対策（どのフェーズで潰すか）                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 利用者の文書へ DLID 以外を書き込む（見出し末尾の置き位置、ATX の閉じの `#`、setext、コードブロック・HTML ブロック内、閉じる行の無い frontmatter） | 高     | フェーズ 1 で最初に実装し、書き込み後の再解析と取消しを必須にする。入力のバリエーションを固定の fixture にして網羅する                                   |
| アンカー生成が github-slugger v2.0.0 と食い違う。設計は Unicode 13.0.0 に固定するが、実行する Python の Unicode の版は異なりうる                  | 中     | フェーズ 1 の早い時点で、版の差が出る文字を実測して差を確かめる。Python 標準の `unicodedata` で足りなければ、固定した文字表の持ち方をユーザーに確認する  |
| ハッシュ規則（title の記録語を除く）の誤りが、通知の連鎖・無限更新を生む                                                                          | 高     | フェーズ 1 のテストベクトルで、相互参照の文書を含めて確かめる。フェーズ 3 で `check-impact` の項目として再確認する                                       |
| 管理状態の書き込み途中の公開、再現できないバイト列による git の差分ノイズ                                                                         | 中     | フェーズ 1 の保存層で、キー整列・UTF-8・インデント固定・内容不変なら書き換えない・`os.replace` をテストする。フェーズ 2 で段階失敗時の旧版保持を確認する |
| `toc-updater` の入力・メッセージに内部許容上限が漏れる（NFR-008）                                                                                 | 中     | フェーズ 2 で、依頼を組み立てる script と再試行メッセージを検査するテストを置く。検証器のエラーは実際の境界を開示しない                                  |
| Agent との受け渡しが破綻する（終了の値が無い、AI が JSON を組み立てる、削除漏れ）                                                                 | 中     | フェーズ 2・3 で、識別値のみ・script が書く・公開後に読む・終了の値・削除、の各点をテストする                                                            |
| 依存の複雑さ（PEP 723 の script ごとの宣言とロック、共通モジュールの置き場、Python 3.15 の可用性）                                                | 中     | フェーズ 1 の最初のタスクで、共通モジュールを使う入口 script が `uv run --locked` で動く構成を確かめ、以降の script の雛形にする                         |
| 構築と検索で使う照合 script が分かれ、判定が食い違う                                                                                              | 中     | フェーズ 3 で `check-toc` と検索前検査を同じ script にする（DES-010 §1.2）。同じ入力で同じ結果になることをテストする                                     |
| AI の判断（`toc-updater`・`query-worker`）の品質は自動テストで保証できない                                                                        | 低     | 決定論的な検証（形・長さ・ID の対応）は script で行う。品質は手動の確認として分けて残し、結果を計画書の検証に記録する                                    |
| 索引検索を経ていない既存仕様の調査（上記「前提の確認」）                                                                                          | 低     | 仕様の置き場が doc-link のみであることを列挙で確認済み。他の仕様が見つかったら、フェーズ 1 の前に戦略を見直す                                            |
