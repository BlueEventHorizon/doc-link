# doc-link 実装戦略

## 前提

- 型: 要件定義・設計とも完全新規（差分 feature の一時マーカーは全 16 文書に無い）。既存実装は無い（リポジトリに `plugins/`・`tests/` が存在しない）。このため「既存実装との不一致」の節は置かない
- 関連する既存の仕様書: `/forge:query-db-specs`（backend: doc-advisor、key `specs`）で検索した結果、doc-link 自身の REQ-001〜005・DES-001〜010・設計書 README だけが該当した。doc-link が依存・接続する別機能の仕様書は本リポジトリに無い
- DocAdvisor は置き換え対象であり、コードや管理データを共有しない（REQ-001 §3）。`toc-updater`・`query-worker` の起動方式と関連度判定の方式は DocAdvisor と同じとされている（DES-006 §2）ため、実装時に DocAdvisor の配布物を**参照する**のはよいが、取り込んで依存はしない
- 配置: `plugins/doc-link/`（`skills/{skill}/`、プラグイン共通の `scripts/`・`agents/`）、テストは `tests/doc-link/{skill}/`（共通 script のテストは共通の置き場）。`plugin.json` の version は新規プラグインの初期値だけを書く

## アプローチ

**選択**: ボトムアップ（決定論的な共通処理 → 管理状態 → 各 SKILL）とリスク駆動の組み合わせ。最もリスクの高い「管理対象 Markdown への書き込み」をフェーズ 1 に置く

**根拠**:

- 7 つの SKILL（DES-010 §1）はどれも、同じ決定論的な処理の上に成り立つ。Markdown 解析、DLID の認識・発行、セクション範囲、内容ハッシュ、リンクの抽出、GitHub と同じ規則でのアンカー生成、対象指定の展開（DES-008、DES-005 §2）である。たとえば `check-toc` と `query-docs` の検索前検査は同じ script を使う（DES-010 §1.2）。参照検査は `index-docs` と `check-links` が共有する。依存グラフは基盤から上へ一方向で深いので、基盤を先に固める
- 技術的な不確実性が最も大きいのは `embed-dlid` の書き込み経路である。markdown-it-py は行内のリンク位置を持たないため、行単位の文字列操作で書き込み、再解析して差分が DLID だけであることを検証し、違えば取り消す（DES-008 §1・§2）。誤れば利用者の文書を壊す。さらに `index-docs` 以降は、全文書に DLID が付いている前提で動く（D-034・D-035）。そのため、書き込み経路を最初に作って検証する
- 状態を持つ処理（ToC 公開版、構築実行、ID 付与、変更影響候補の報告）は、DES-004 の遷移表で許可遷移が閉じている。テストの規範も DES-009 に揃っているため、スケルトン先行で早期に E2E を通す必要は薄い。各フェーズの終わりに、遷移表に基づくテストで検証できる
- フィーチャースライスは採らない。どの SKILL も単独では価値が閉じず（検索には構築が要り、構築には ID 付与が要る）、利用者に見せる最小単位は `embed-dlid` → `index-docs` → `query-docs` の縦断になる。これはボトムアップの順序と一致する

## 着手前に確定が必要な事項（設計の不足）

無い。設計書には、実装前に確定すべき未定義の事項は残っていない。

script の分割と CLI の引数形式（DES-002 §4）、および JSON ファイルの物理スキーマ（DES-003 §1 は論理モデルだけを定める）は内部実装なので、計画・実装で決める。ただし物理スキーマは DES-003 §2 の全論理情報を最初から収める（後述のリスク R-4）。

## フェーズ

### フェーズ 1: Markdown 基盤と ID 付与（`embed-dlid`）

- **目標**: 指定したディレクトリ・パス・グロブと除外の Markdown について、次の処理を行い、DLID 以外の差分が出ないことを再解析で検証できる。差分が出れば取り消して報告する
  - 文書 ID が無い文書に `doc_link_id` を書く
  - DLID の無い全見出しにアンカー行を書く
  - title に DLID の無いリンクへ参照先の DLID を加える
  - 重複 ID の原本候補を示し、利用者が確定した原本以外へ再発行する
- **スコープ**:
  - プラグインの骨格（`plugin.json`・marketplace の登録、テストの置き場）
  - 共通 script
    - frontmatter から DLID を認識し、認識できない値をすべて「文書 ID が存在しない」に統一する（DES-008 §1、FR-002）
    - DLID を発行する（60 ビットの `secrets` 乱数、小文字 Crockford Base32 12 文字。D-028）
    - markdown-it-py で見出し・アンカー行・セクション範囲・インラインリンク／リファレンスリンク定義の title を抽出し、リンクの解析規則 1〜10（スキーム付きの宛先と画像を除く、パス部分とフラグメントのパーセントデコード、`#` での分割を含む）に従って参照を取り出す（DES-008 §2）
    - 見出し文字列から GitHub と同じ規則でアンカーを生成する（DES-008 §2）
    - 文書とセクションの内容ハッシュを SHA-256 で算出する（DES-008 §3）
    - 対象指定の引数の組み合わせを検証し、展開する（DES-005 §2 の 1・2。`index-docs` と共有する）
  - JSON 管理状態のスキーマ（DES-003 §2 の全論理情報。置き場は `.doc-link/`、ファイルの分け方は DES-002 §4）。本フェーズでは、全キーの DLID の照合に読み取りだけで使う（D-030）
  - `embed-dlid` の付与計画・書き込み・再解析検証・結果返却（DES-005 §2.1、DES-008 §1、DES-010 §3.1）と、遷移 E-01〜E-07（DES-004 §5）
- **検証ポイント**:
  - 早期（グループ最初の 1〜2 タスクの完成時点）: DLID の認識・発行と Markdown 解析（見出し・アンカー行・セクション範囲・リンク title）の単体テストが通る。DES-008 §2 の解析規則 1〜10 のテストが通る。対象指定の引数の組み合わせ（DES-005 §2 の 1）のテストが通る。DES-008 §3 の内容ハッシュのテストベクトルが通る。具体的には、本文・見出し・リンクの表示文字列・リンク先・title・DLID の追加のどれでもハッシュが変わり、セクション範囲の外だけを変えた場合はそのセクションのハッシュが変わらない
  - 書き込みの単体テスト: アンカー行の前後の空行の規則、既存 title の末尾への追記と囲み記号の保持、コードブロック・HTML ブロックへ書き込まないこと、frontmatter を解析できない文書は報告だけすること、DLID 以外の差分を検出したら取り消すこと
  - 遷移表のテスト: E-01〜E-07 の全行、ガード不成立、表に無いイベント。途中失敗の後の再実行で、書き込み済みの DLID を既存として照合し直すこと（DES-009 §1）
  - 本リポジトリの `docs/` の写しで実行し、差分が DLID だけであることを `git diff` で目視確認する（本物の `docs/` には書き込まない）
  - 単体テストのコマンド（CLAUDE.md）がすべて通る。`dprint check` が通る

### フェーズ 2: ToC 構築（`index-docs`）と情報生成 Agent

- **目標**: 管理キーと完全な対象指定から ToC を構築・再構築し、検査済みの候補だけを一括で公開できる。ID 未付与・重複の文書は除外して報告し、構築は止めない。変更が無い文書・パスだけが変わった文書は、AI に再生成させない。失敗したときは旧確定版を保持する
- **スコープ**:
  - `index-docs` の段階 B-01〜B-09（DES-004 §3）。対象確定、ID 確認（D-036）、変更集合の確定（DES-005 §3）、更新計画と必要情報の取得（DES-005 §4）、参照の実走査（DES-007 §1。`check-links` と共有する script として作る）、候補の検査と一括確定、ToC 公開版の P-01〜P-03（DES-004 §2）
  - 書き込みの単位: 文書情報と、キー別の索引状態の一括公開を、それぞれ一時ファイルからの置き換え（`os.replace`）で行う（DES-005 §5）。同じ内容から同じバイト列を出力し、内容が変わらないファイルは書き換えない（DES-002 §4）
  - カスタム Agent `toc-updater` と受け渡しの script（DES-010 §4、`agent_data_exchange_rules.md`。置き場は `.temp/doc-link/<skill>/`、DES-002 §4）。AI 出力の検証器（`L` と `H = floor(L × 1.3)`、Unicode コードポイント数。DES-008 §4、D-044）
  - 正規化した管理対象指定を版に保存し、再解釈できるようにする（D-020）
  - タイトルの取得: 最初の H1 見出しのテキストとし、H1 が無い文書だけ `toc-updater` に生成させる（DES-008 §4）
- **検証ポイント**:
  - 早期: 対象確定 → ID 確認 → 変更集合の確定まで（AI を呼ばない部分）を、初回（全件が新規）と再構築（パスだけ・本文・参照・離脱が併存）のテストで通す（AC-025・AC-026）
  - 検証器の境界テスト: `L+1`〜`H` を受理し、`H+1` を拒否する（AC-010）。`toc-updater` の定義・依頼・再試行メッセージに `H`・係数・余白が含まれないことを機械的に検査するテストを置く（AC-011、NFR-008）
  - 遷移表のテスト: B-01〜B-09 と P-01〜P-03。各段階の失敗で旧版を維持すること。それまでに確定した文書情報は戻さないこと（DES-004 §3、D-024）
  - 参照検査のテスト: 一致、パス不一致、指定ディレクトリ内に不在、ディレクトリ自体の不在、ディレクトリを読めない場合。いずれも確定を妨げないこと。フラグメント不一致（AC-028、D-025）
  - 複数キーの隔離: A の更新が B の ToC を変えないこと。同じ ID・内容ハッシュの文書は B への追加だけで再生成しないこと（AC-021・AC-029、DES-009 §3 の 5）
  - 構築が管理対象 Markdown を書き換えないこと（AC-030）
  - 管理状態のファイル: 同じ入力から同じバイト列を出力すること、内容が変わらないファイルを書き換えないこと、一時ファイルを `.temp/doc-link/<skill>/` 以外に作らないこと（DES-002 §4）
  - AI を含む実行（`toc-updater` の生成）は手動のテストとして分けて置き、フェーズ 1 で DLID を付けた `docs/` の写しで一度通す

### フェーズ 3: 文書検索（`query-docs`・`check-toc`）

- **目標**: 確定版がある key で、検索前検査の 4 つの結果（未構築／再構築不要／再構築必要／判定不能）を区別できる。再構築が必要なら、規模を示して利用者に二択を確認する。判定不能なら障害として止める。検索結果に、使用した版と鮮度を添えて返す
- **スコープ**:
  - 検索前検査の script（DES-006 §1）。`check-toc` と同じ script とする（DES-010 §1.2）。規模の件数として、新規・離脱・パス変更・内容変更・ID 未付与・ID 重複と、AI 生成が必要な件数を返す（D-027）
  - `check-toc` の SKILL（DES-010 §3.6）
  - `query-docs` の SKILL と、カスタム Agent `query-worker`（DES-006 §2、DES-010 §3.3・§4）。版で固定した ToC の写しを渡す。返った ID が版に無い結果は異常として扱う
  - 既存版のまま検索する場合の扱い: キー別の索引状態は旧版を使い、文書情報は最新のものを使う（D-024）
- **検証ポイント**:
  - 早期: 検索前検査の script 単体で 4 区別のテストを通す。frontmatter を解析できない文書は ID 未付与として数え、対象ディレクトリの消失は再構築必要とし、どちらも判定不能にしないこと（DES-006 §1）
  - AC-019 の各分岐
  - 既存版のまま検索しても、ToC と比較基準が変わらないこと
  - `query-worker` の結果検査: 存在しない ID を含む結果を失敗にすること
  - AI を含む検索は手動のテストとして通す

### フェーズ 4: 検査と変更影響候補の通知（`check-dlid`・`check-links`・`check-impact`）

- **目標**: FR-016 の不整合を、3 つの検査 SKILL で列挙できる。`check-impact` は、ToC が最新のときだけ、未報告の変更とその直接の参照元を返す。そのとき、返した (変更された文書またはセクション, 参照元) の組の処理済み比較基準を同じ操作で進める。進められなかったときは報告せず、次回に同じ変更を報告する
- **スコープ**:
  - `check-dlid`（DES-010 §3.4。フェーズ 1 の DLID の認識と照合を再利用する）
  - `check-links`（DES-010 §3.5。フェーズ 2 の参照検査の script を再利用する。title に DLID の無いリンクと、存在しないセクションの判定は DES-007 §4）
  - `check-impact`（DES-007 §2・§3、DES-010 §3.7）と遷移 N-01〜N-05（DES-004 §6）
    - 処理済み比較基準は (DLID, 参照元 ID または「参照元なし」) の組ごとに管理する
    - セクションの追加と変更を区別する
    - ToC に無くなったセクションの基準は、通知せずに除去する
    - どのキーにも所属しなくなった文書の基準は除去する（D-046）
- **検証ポイント**:
  - 早期: `check-dlid` と `check-links` は既存の script の組み合わせなので、最初に作り、FR-016 の項目ごとのテストを通す
  - `check-impact` の遷移表のテスト（N-01〜N-05）。DES-009 §1 の比較基準のシナリオを通す。具体的には、進められなかった場合の再報告、「参照元なし」の記録と、後から参照元が加わった場合の報告、片方のキーからの離脱では基準が残り全キーから離脱すると除去されること、セクションの追加と変更の区別
  - AC-006〜AC-009（AC-007 のセクション単位の限定を含む）
  - 検査の SKILL が管理状態を書き換えないこと。例外は `check-impact` の比較基準だけ
  - DES-009 §3 の横断シナリオ 1〜7 を、DLID を付けた `docs/` の写しで手動で通す
