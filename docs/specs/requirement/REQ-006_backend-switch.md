# doc-link 要件定義書 — 検索基盤の切り替え DLID-4042ef3rdqs9

[総論][req-001] · [Index 対象と文書 ID][req-002] · [ToC 管理][req-003] · [文書検索][req-004] · [参照と変更通知][req-005] · [検索基盤の切り替え][req-006]

## 18. 検索基盤の切り替え DLID-06wcf22rjcdy

本書は、[ToC]の構築と文書検索の裏側（[検索基盤]）を、[doc-db]と[ToC]で切り替える要件を定める。本書は差分開発型の文書であり、既存の要件定義書（REQ-001〜REQ-005）の本文は、実装が終わるまで書き換えない。

- REQ-003 と REQ-004 は、[検索基盤]が[ToC]のときの要件として読む。
- 本書は、[検索基盤]が[doc-db]のときの差分と、切り替えの規則を定める。
- 本書と既存の要件が食い違う点（§18.9）は、利用者の承認を得てから既存の文書へ統合する。

### 18.1 範囲と用語 DLID-vs1s6jpez375

[検索基盤]は、[doc-db]と[ToC]の 2 つである。

- [doc-db]を使うとき、[AI 生成フィールド]は作らない。文書の検索は[doc-db]が行う。
- [ToC]を使うとき、現在の動作どおり、[AI 生成フィールド]を作り、[検索 AI]が文書を読んで検索する。
- [確定 ToC]のうち、機械取得の情報（[文書 ID]、現在のパス、[内容ハッシュ]、セクション、参照関係）は、[検索基盤]によらず常に構築する。[DLID]の管理状態を保つためである（D-070）。
- [AI 生成フィールド]だけが、[検索基盤]に依存する。

切り替えの範囲は、[ToC]の構築と文書検索の両方である（D-064）。

### FR-019 検索基盤の既定 DLID-qxmk354vw8v5

プラグインは、[doc-db]が動作するときは、[AI 生成フィールド]を作らず、[doc-db]で索引を構築して検索すること（D-064）。[doc-db]が動作するとは、[doc-db]へ接続でき（接続できなければ、プラグインが起動して接続する。FR-027）、[doc-db]の機能（検索・同期・Embedding）が失敗していないことを指す。

### FR-020 強制スイッチ DLID-5xay6r1be1c5

プラグインは、[doc-db]が動作するときでも、[ToC]を使うことを明示的に指定できる[強制スイッチ]を持つこと（D-065）。[強制スイッチ]は、設定ファイルで指定する。毎回の呼び出しで指定することを、利用者に求めない。

- [強制スイッチ]が指定されたとき、プラグインは[doc-db]へ接続せず、起動もせず、[ToC]で構築と検索を行う。
- [強制スイッチ]は、[自動切り替え]（FR-021）とは別の仕組みである。[強制スイッチ]は利用者の指定であり、障害の検出を必要としない。
- 設定が未指定のときは、[doc-db]を先に試す（FR-019）。設定が読めない・値が不正なときは、失敗として原因を返す。黙って既定の動作にしない。
- 設定ファイルの置き場・名前・形式は、設計で定める。

### FR-021 自動切り替え DLID-p310fey990k1

プラグインは、次のときに、[ToC]へ自動で切り替えること（D-066）。

- (a) [doc-db]に接続できない（未導入、または起動を試みても接続できない場合を含む。FR-027）
- (b) [doc-db]へ接続できたが、OpenAI が失敗した（検索の失敗、または文書の Embedding の失敗）

次の規則に従う。

- (a) と (b) 以外の失敗（たとえば、[doc-db]の KEY の状態の異常、同期の完了待ちの超過）では、切り替えない。失敗として、原因と次の判断に要る情報を返す。説明できない切り替えで、失敗を隠さないためである。
- 切り替えは、その実行にだけ作用する。プラグインは、切り替えたことを保存しない。次の実行は、再び[doc-db]を先に試す。
- 切り替えた実行は、[ToC]で、構築または検索を最後まで行う（FR-022）。

### FR-022 [ToC]への切り替え後の構築 DLID-j3azdgm64pqp

[ToC]で構築または検索を行うとき、[AI 生成フィールド]が未生成の文書、または[内容ハッシュ]が変わった文書があれば、その場で[AI 生成フィールド]を作ること（D-067）。

- [ToC]が無い場合も同じである。他に検索の手段が無いためである。
- 次の場合は、[FR-006][req-004-fr-006]の「再構築してから検索する」と「既存の[ToC]のまま検索する」の二択を示さず、構築する。再構築の規模は、利用者へ通知する。
  - [確定 ToC]に含まれる文書に、[AI 生成フィールド]が未生成の文書がある。既存の[ToC]のままでは検索できず、取りこぼすためである。
  - [確定 ToC]の機械取得の情報は最新（再構築が不要）なのに、[AI 生成フィールド]が古い文書がある（[doc-db]を使っていた間に変わった文書）。既存の[ToC]のままだと、古い[AI 生成フィールド]を最新として検索してしまうためである。
- 上記以外では、[ToC]を使うときの規則は変わらない。[確定 ToC]の機械取得の情報が古いときは、[AI 生成フィールド]が古い文書があっても、二択を示す（既存の規則）。
- 既に生成済みで[内容ハッシュ]が変わっていない文書は、再生成しない（[FR-005][req-003-fr-005]）。[doc-db]を使っていた間に変わった文書だけが、生成の対象になる。

### FR-023 切り替えの通知 DLID-teevqc3s1v6d

プラグインが[ToC]へ切り替えたとき、AI が、切り替わったことを利用者に知らせること（D-068）。通知には、次を含める。

- 切り替えたこと（[doc-db]から[ToC]へ）
- 理由（(a) 接続できない、(b) OpenAI の失敗のどちらか）と、確認できた原因。認証情報と、[doc-db]の応答の生の文字列は含めない
- 影響（[AI 生成フィールド]を作る文書の件数、検索の結果の性質が変わること）
- 次の実行でも、再び[doc-db]を先に試すこと

[強制スイッチ]で[ToC]を使うときは、切り替えではないので、この通知を行わない。使った[検索基盤]は、結果に常に含める。

### FR-024 [doc-db]の更新 DLID-z0yzq2wwxee1

[doc-db]は、文書のパスの変更・移動・削除を知らない。プラグインは、管理状態から現在の文書の一覧を作り、[doc-db]へ渡して、[doc-db]の内容を更新すること（D-069）。

- 一覧は、[確定 ToC]に所属する文書とその現在のパスから作る。一覧に無い文書は、[doc-db]の検索の対象から外れる。
- 文書が移動したとき、削除されたとき、追加されたときに、[doc-db]の検索結果が、変更前のパスを返し続けないこと。
- [doc-db]へ渡すのは、文書の本文の取得元とパスだけである。[DLID]を[doc-db]の識別子（KEY・パス）として渡さない。
- [doc-db]を使うとき、検索の前に、[確定 ToC]が現在の[Index 対象文書]と食い違っていれば、機械取得の構築と[doc-db]の更新を自動で行う。FR-006 の二択（再構築してから検索する・既存の[ToC]のまま検索する）を示さない（D-072）。[doc-db]の更新に AI 生成が要らず、費用が小さいためである。再構築の規模は、利用者へ通知する。
- 検索の前に、[doc-db]が[確定 ToC]の一覧と食い違っていないことを保証すること。更新の時点は、設計で定める。
- [Index 対象指定]が渡されず、[確定 ToC]が未構築のときは、自動で更新できない（対象を決められない）。初回の構築が必要と返す。

### FR-025 [doc-db]を使うときの検索結果 DLID-j457th355zzz

[doc-db]を使うときの検索結果は、[FR-006][req-004-fr-006]の検索結果と同じ項目を持つこと。

- [文書 ID]、[確定 ToC]に記録されたパス、関連すると判断した理由、必要に応じて該当セクション、使用した[ToC]の状態（[ToC 識別キー]・版・鮮度）を含める。
- [doc-db]はチャンクごとの結果を返し、[DLID]の欄を持たない。プラグインは、[doc-db]が返したパスと見出しを、管理状態を用いて[文書 ID]と[セクション ID]へ対応づける。対応づけられない結果は、結果の文書に含めず、件数を報告する。
- 使った[検索基盤]（[doc-db]か[ToC]か）を結果に含める。
- [doc-db]の検索は、上位の結果に限られる。[FR-006][req-004-fr-006]の「関連するかどうか迷う文書を結果に含める」は、満たせない。この限界を、結果に明示する。上位の件数は TBD とする。
- [doc-db]は、意味的な関連の判定を返さない。結果の関連の強弱（`yes`・`maybe`）は、`maybe`（判断がつかないが、関連するかもしれない）とする。

### FR-026 [DLID]と管理状態の独立 DLID-jy4phq1hnd2m

[DLID]の発行・書き込み・管理・解決は、[検索基盤]によらず、プラグインだけが行うこと（D-070）。

- [doc-db]の動作は、[DLID]に依存しない。[doc-db]は、本文に含まれる[DLID]の文字列を、本文の一部として扱う。
- `check-dlid`・`embed-dlid`・`check-links`・`check-toc`・`check-impact`・`resolve-dlid` は、[検索基盤]によらず、同じ結果を返すこと。[doc-db]を使っている間も、[DLID]の管理状態（[文書 ID]・パス・[内容ハッシュ]・セクション・参照関係）を、現在の文書に対して保つ。
- [doc-db]を使っている間に[AI 生成フィールド]を作らないことで、[内容ハッシュ]が変わった文書の[AI 生成フィールド]は古くなる。[ToC]へ切り替えたとき、古い[AI 生成フィールド]を現在のものとして使わない（FR-022）。

### FR-027 [doc-db]の起動 DLID-tmyfwg26n6ss

プラグインは、[doc-db]へ接続できないとき、[doc-db]を起動し、期限を設けて再接続すること（D-071）。

- 起動しても期限内に接続できないとき、(a) として[ToC]へ切り替える（FR-021）。
- 起動は、その実行を完了するためだけに行う。プラグインは、[doc-db]を停止せず、常駐させる設定（OS の自動起動・サービスへの登録）をせず、監視・再起動をしない。起動した[doc-db]は、その実行の後も動き続けうる。
- [強制スイッチ]が指定されているときは、起動しない。
- 起動の引数・ポート・ログの出力先は、[doc-db]自身の設定に任せる。プラグインは、ログのファイルを作らない。
- 起動に失敗した原因（実行ファイルが無い、起動できない、接続の前に終了した、期限内に接続できない）を、通知で区別できること。

### FR-028 [doc-db]に求める契約 DLID-w17kedmxgr9s

プラグインが[doc-db]に求める契約を、次に示す（D-073）。[doc-db]の修正は[doc-db]側で行う。[doc-db]の既存の tool・入出力は、互換のために変えない。契約は、識別子などの追加と、Embedding が欠けた文書の扱いだけである。プラグインは、既存の入出力（`sync_documents`・`get_sync_status`・`query` の既存の項目）を前提にする。

**エラーの識別子.** プラグインは、失敗の判別を、識別子だけで行う。識別子の置き場は、JSON-RPC のエラーの `error.data.code`（検索など。数値の `error.code` は従来のまま。OpenAI の HTTP の状態コードを確認できたときは `error.data.http_status` も付く）、同期ジョブの応答の `document_errors[].code`（文書ごとの失敗）、失敗したジョブの最上位の `code` である。文言・数値の `code` では判別しない。

| 識別子             | 意味                                                                                                            | 返す場面                                                     | プラグインの扱い                     |
| ------------------ | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------ |
| `KEY_NOT_FOUND`    | KEY が存在しない（既存）                                                                                        | 検索                                                         | 同期の直後なら障害                   |
| `KEY_TRASHED`      | KEY がゴミ箱にある（既存）                                                                                      | 検索・同期                                                   | 障害                                 |
| `EMBEDDING_FAILED` | OpenAI から Embedding を得られなかった。再試行を尽くした後の失敗で、認証・通信・HTTP のエラー・応答の不正を含む | 検索のクエリの Embedding。同期での文書のチャンクの Embedding | OpenAI の失敗 (b)。[ToC]へ切り替える |
| `INTERNAL_ERROR`   | 上記以外のサーバー内部の失敗（保存先・ファイルの読み取りなど）                                                  | 任意                                                         | 障害。切り替えない                   |

- 契約を満たす[doc-db]は、サーバー内部の失敗に、必ず識別子（`EMBEDDING_FAILED` か `INTERNAL_ERROR`）を付ける。入力の不正（JSON-RPC `-32602`。key が空、job_id が不明など）は、識別子を付けない。識別子の無いエラーは、障害として扱う。
- 同期ジョブが完了（`done`）しても、Embedding に失敗した文書がありうる。`get_sync_status` の応答は、文書ごとの失敗を `document_errors`（`path`・`code`・`skipped_chunks`（あれば）の配列。失敗が無ければ空）に、常に持つ。既存のエラーの文字列の一覧 `errors` は、他の利用者のために維持される。

**Embedding が欠けた文書の扱い.** 同じ KEY・series・パス・内容の文書でも、Embedding が欠けたチャンクを持つ文書は、同期で skip しない。欠けたチャンクだけを、再度 Embedding する。成功すれば完全になり、再び失敗すれば、上記の識別子で報告する。

**プラグインから見た振る舞い.**

- エラーが無く完了した同期の後、[doc-db]は一覧と一致し、Embedding の欠けた文書は無い。
- OpenAI の失敗で不完全になった同期の後、次の同期が、OpenAI の復旧を待って、[doc-db]を完全にする。プラグインは、[doc-db]の内容を削除せず、失敗を記録しない。
- 切り替えた実行も、次の実行で[doc-db]を先に試す（FR-021）。

**契約を満たさない[doc-db]（当面の扱い）.** プラグインは、同期ジョブの応答に `document_errors` があるかで、契約を満たす[doc-db]かを判断する（版の番号では判断しない。契約を満たす最初の[doc-db]の版は 0.4.1 で、記録するだけである）。目印が無いときは、満たさない[doc-db]として扱う。満たさない[doc-db]では、次のとおり扱い、結果の警告に、契約を満たさない[doc-db]であることを含める。

- 識別子の無い、検索の内部エラー（JSON-RPC の `-32603`）を、(b) とみなす。原因は推定であることを通知に明記する。
- 同期ジョブの Embedding の失敗は、エラーの文言（`embed:` で始まる）で判別する。
- Embedding が欠けた文書が、内容が変わるまで補われないことがありうる。

### NFR-009 認証情報の非取扱い DLID-mc29rz833cbk

プラグインは、OpenAI の認証情報を読まず、[doc-db]へ渡さず、出力・作業ファイル・管理状態に含めないこと。[doc-db]への接続の失敗・OpenAI の失敗を通知するときは、失敗の分類と、確認できた HTTP の状態コードだけを含める。
