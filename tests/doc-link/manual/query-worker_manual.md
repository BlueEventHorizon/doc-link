# query-worker の判断品質の手動確認

実際の `query-worker`（AI）が、script から 1 件ずつ受け取った文書について、関連するかを判断する品質を、手動で確かめる手順。AI の判断は揺れ、実行に費用がかかるので、自動で実行するテスト（`test_*.py`）に入れない。受け渡しの仕組み（担当の分割・依頼・答え・終了の値・検査・削除）は、AI を介さない自動テストが確かめている。ここで確かめるのは、AI が担当の文書のすべてに、意味で関連するかを判断し、script へ答えられるかである。

## 目的

- `query-worker` が、script が見せる文書を 1 件ずつ読み、タスクに関連するかを、関連理由とともに答えられる
- 語句の一致だけで選ばず、意味で選べる
- 担当の文書を飛ばさず、まとめて答えず、文書を指す名前も ID も番号も書かない
- 存在しない見出しを書かず、引き当てられなかったときは、script が返す候補から選び直せる
- 再構築不要の場合と、再構築が必要で既存版のまま検索を選んだ場合の両方で、使用版と鮮度が結果に付く
- 検索が[ToC]・管理状態・文書を書き換えない

## 事前条件

- `doc-link` プラグインが読み込める環境で、`uv` が使える
- 確認用のプロジェクトを新しく用意する（確認のたびに空の状態から始める。本リポジトリの管理状態を使わない）
- 確認用のプロジェクトに、`doc_link_id` を持つ文書を置く。意味の近い文書と遠い文書を含める
  - 検索のタスクに意味として関連する文書（タスクの語句を本文にあまり含まないものを 1 つ以上含む）
  - 語句は似ているが、意味としては関連しない文書
  - 関連するかどうか判断が分かれる文書（タスクの周辺の話題を扱う文書）
  - 明らかに無関係な文書
  - 見出しを複数持ち、一部の見出しだけが関連する文書
- `index-docs` で[ToC]を構築済みにする
- `.temp/` を `.gitignore` に含める

## 手順

1. 再構築不要の場合: 構築直後の状態で、`query-docs` を検索のタスクとともに実行する。実際の `query-worker` が Agent ツールで起動される
2. 結果を確認する（下記）
3. 再構築が必要で既存版のまま検索を選んだ場合: 文書を 1 つ変更して（内容を書き換える、または新しい文書を足す）から、`query-docs` を実行する。二択の確認で、「既存の[ToC]のまま検索する」を選ぶ
4. 結果を確認する（下記）
5. 親の指示に実装・編集の依頼を含めた場合: 親の指示に「検索して、見つかった文書を直して」と書いて `query-docs` を実行し、`query-worker` が検索だけを行い、文書を編集しないことを確かめる
6. 関連する文書が無いタスクで実行し、0 件の結果が正常に返ることを確かめる

## 期待する結果（確認の観点）

| 観点           | 内容                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 選ばれる文書   | 意味として関連する文書が選ばれている（語句の一致が少ない文書も含む）                                                              |
| 選ばれない文書 | 明らかに無関係な文書が選ばれていない                                                                                              |
| 迷う文書       | 関連するかどうか判断が分かれる文書（周辺の話題を扱う文書）が、`no` にされず、`maybe` で結果に含まれている（明らかな関連は `yes`） |
| 関連理由       | 文書がタスクにどう関連するかを説明していて、妥当である                                                                            |
| 全文書         | 担当の最後の文書にも答えている（途中で終えて、検索の失敗にならない）                                                              |
| 担当の分割     | 文書が多いとき、担当ごとに `query-worker` が並列に起動され、全担当の答えが揃っている                                              |
| 見出し         | 返った見出しが、その文書の見出しに引き当てられる。外れたときは、候補から選び直せている                                            |
| セクション     | 一部の見出しだけが関連する文書で、該当する[セクション ID]が結果に付いている                                                       |
| 並び           | 担当の順と担当の中の順（パスの昇順）であり、関連度の順ではない（`order_notice` がある）                                           |
| 0 件           | 関連する文書が無いとき、すべての文書に `no` と答え、0 件が正常な結果として返る                                                    |

進行の観点として、次も確かめる。

- 再構築不要のとき、結果の鮮度が最新である。既存版を選んだとき、結果に使用した[ToC]の版と、古い可能性があること（`freshness_notice`）が付き、現在の[Index 対象リスト]を反映していない可能性が結果全体に明示される
- パスは、記録されたパスとして返り、現在の実体パスとして断定されていない
- Agent の応答は、終えたことと理由だけで、選んだ文書や関連理由の内容を含まない
- 検索の前後で、[ToC]・管理状態（`.doc-link/`）・文書が書き換わっていない（`git status` や差分で確認する）
- 検索が終わった後、`.temp/doc-link/query-docs/` に検索の作業ファイル（検索 ID のもの）が残っていない
- 親の指示に実装・編集の依頼を含めても、`query-worker` がそれを実行しない

## 結果の記録

結果は、計画書の検証に記録する前提で、次の形で書く。

```text
確認日: YYYY-MM-DD
確認者: （名前）
環境: （Claude Code のバージョン、プラグインのコミット）
文書: （確認した文書の構成。意味の近い文書・遠い文書・セクション単位の関連）
検索のタスク: （確認に使ったタスク）
結果: 合格 / 不合格
不合格の内容: （観点・文書・観測した結果）
備考: （揺れた点、再実行した回数、気づいたこと）
```

- 観点ごとの合否を 1 行ずつ書く。合格だけを書かず、確認した観点の一覧を残す
- 不合格のときは、同じ指定で再実行して再現するかを書く。再現しない揺れは、再現しなかったことを記録する
- 不合格の原因が `query-worker` の定義（指示の不足）と考えられるときは、定義を直す。検査の仕組み（その文書に無い見出しを引き当てない検査、答えの無い文書が残る検索を失敗とする検査）を、この確認の結果に合わせて変えない
