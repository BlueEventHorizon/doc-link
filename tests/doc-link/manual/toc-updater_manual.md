# toc-updater の生成品質の手動確認

実際の `toc-updater`（AI）が生成する[文書情報]の品質を、手動で確かめる手順。AI の判断は揺れ、実行に費用がかかるので、自動で実行するテスト（`test_*.py`）に入れない。受け渡しの仕組み（依頼・結果・終了の値・検証・削除）は、AI を介さない自動テストが確かめている。ここで確かめるのは、AI が依頼を読み、本文から値を生成し、script へ渡せるかである。

## 目的

- `toc-updater` が、依頼のファイルを読み、対象文書の本文から、記述上限 `L` に収まる値を生成できる
- 生成した値が、`index_docs.py deliver` を通って検証に受理され、[文書情報]として保存される
- 値が英語で書かれ、H1 の見出しがある文書ではタイトルを生成しない
- 対象文書を読めないとき、`toc-updater` を起動する前の段階で、構築の失敗として報告される（`source_unreadable` を渡す経路は、AI を介さない自動テストが確かめている）

## 事前条件

- `doc-link` プラグインが読み込める環境で、`uv` が使える
- 確認用のプロジェクトを新しく用意する（確認のたびに空の状態から始める。本リポジトリの管理状態を使わない）
- 確認用のプロジェクトに、次の文書を置く
  - 日本語の本文を持つ文書（H1 の見出しあり）
  - 英語の本文を持つ文書（H1 の見出しあり）
  - H1 の見出しが無い文書（本文だけ）
  - 本文が長い文書（記述上限を超えそうなほど多くの話題を含む）
- 文書の frontmatter に `doc_link_id` を持たせておく（`embed-dlid` で付与するか、手で書く）
- `.temp/` を `.gitignore` に含める

## 手順

1. 確認用のプロジェクトで、`index-docs` を `--paths` で上の文書を指定して実行する。実際の `toc-updater` が Agent ツールで起動される
2. 完了後、`index-docs` の報告で `published` が真であることを確かめる。失敗したときは、報告の `stage`・`problems` を記録する
3. `.doc-link/documents/` の文書ごとのファイルを開き、フィールドを確認する（下記）
4. 対象文書を読めない場合の確認: 1 つの文書の権限を外して（または削除して）から、`index-docs` を実行する。`toc-updater` が起動される前の段階で、文書を読めない失敗が報告されることを確かめる
5. 同じ指定でもう一度 `index-docs` を実行し、生成を依頼されず、[文書情報]が書き換わらないことを確かめる

## 期待する結果（確認の観点）

文書ごとの[文書情報]について、次を確かめる。

| フィールド         | 観点                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `title`            | H1 の見出しがある文書は、見出しのテキストである（`toc-updater` が値を作っていない）      |
| `title`            | H1 の見出しが無い文書は、文書を表す英語のタイトルである                                  |
| `purpose`          | 200 文字以内で、文書の目的を表している。英語である                                       |
| `summary`          | 5 要素以上 10 要素以内で、文書の内容を表している。英語である                             |
| `applicable_tasks` | 1 要素以上 10 要素以内で、その文書を参照すべき作業になっている。英語である               |
| `keywords`         | 5 要素以上 10 要素以内で、検索に使える語になっている。英語である                         |
| 全体               | 文書どうしの内容が混ざっていない（同じ起動で受け持った別の文書の話題が入っていない）     |
| 全体               | 記述上限を超えて拒否された文書が無い。拒否されたときは、フィールドと上限だけが報告される |

進行の観点として、次も確かめる。

- 報告・Agent の応答・拒否の報告に、記述上限 `L` を超える内部の数値や、係数・余白に当たる語が現れない
- Agent の応答は、終えたことと理由だけで、生成した値の内容を含まない
- 対象文書・管理状態の文書情報以外のファイルが書き換わっていない（`git status` や差分で確認する）
- 構築が終わった後、`.temp/doc-link/index-docs/` に `BUILD-` で始まるものが残っていない

## 結果の記録

結果は、計画書の検証に記録する前提で、次の形で書く。

```text
確認日: YYYY-MM-DD
確認者: （名前）
環境: （Claude Code のバージョン、プラグインのコミット）
文書: （確認した文書の種類。日本語・英語・H1 なし・長文）
結果: 合格 / 不合格
不合格の内容: （フィールド・文書・観点・観測した値）
備考: （揺れた点、再実行した回数、気づいたこと）
```

- 観点ごとの合否を 1 行ずつ書く。合格だけを書かず、確認した観点の一覧を残す
- 不合格のときは、同じ指定で再実行して再現するかを書く。再現しない揺れは、再現しなかったことを記録する
- 不合格の原因が `toc-updater` の定義（指示の不足）と考えられるときは、定義を直す。検証の仕組み（上限・検証器）を、この確認の結果に合わせて変えない
